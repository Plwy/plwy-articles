 我用一个"外卖平台"的类比，帮你理解这三个核心概念，然后给出技术实现。

---

## 外卖平台类比

想象你经营一个**美团外卖**平台：

```
用户下单 → 平台调度 → 骑手配送
          ↑
    这里需要解决三个问题
```

| 概念         | 外卖平台对应         | 核心问题           |
| ------------ | -------------------- | ------------------ |
| **服务发现** | 哪些骑手在线？在哪？ | 如何找到可用的服务 |
| **负载监控** | 骑手忙不忙？累不累？ | 服务健康状况如何   |
| **负载均衡** | 派单给哪个骑手？     | 如何把请求合理分配 |

---

## 1. 服务发现（Service Discovery）

### 类比：骑手上线打卡
```
骑手A 打开APP → 上报位置："我在朝阳区，可接单" → 平台记录在册
骑手B 打开APP → 上报位置："我在海淀区，可接单" → 平台记录在册
用户下单时 → 平台查表："朝阳区有骑手A，派给他"
```

### 技术定义
> **自动注册服务地址，让调用方找到可用实例**

### 实现方式

#### 方式A：DNS + 静态配置（简单）
```yaml
# config.yaml - 写死地址（问题：机器挂了不知道）
user-service:
  - 10.0.1.5:8080
  - 10.0.1.6:8080
```

#### 方式B：注册中心（主流）
```python
# 服务启动时自动注册
import consul  # 或 etcd, zookeeper, nacos

c = consul.Consul()

# 服务A启动，向注册中心"打卡"
c.agent.service.register(
    name="order-service",
    service_id="order-001",
    address="10.0.1.5",
    port=8080,
    check=consul.Check.http("http://10.0.1.5:8080/health", interval="10s")
    # ↑ 每10秒心跳检测，挂了自动剔除
)

# 服务B调用服务A时，先查询注册中心
services = c.health.service("order-service")[1]
# 返回所有健康的实例地址，选一个调用
```

#### 方式C：Kubernetes 原生（云原生）
```yaml
# K8s 自动完成服务发现
apiVersion: v1
kind: Service
metadata:
  name: order-service  # 这个名字就是DNS
spec:
  selector:
    app: order          # 自动找到所有带这个标签的Pod
  ports:
    - port: 80
```

## 2. 负载监控（Load Monitoring）

### 类比：骑手状态监控
```
平台实时监控：
├─ 骑手A：已接3单，预计30分钟完成 → 健康，可继续派单
├─ 骑手B：已接8单，超时2单       → 警告，减少派单
└─ 骑手C：GPS不动，5分钟没响应    → 异常，标记离线
```

### 技术定义
> **收集服务指标，判断健康状态，触发告警或自动处理**

### 监控维度

| 层级         | 指标                      | 工具                       |
| ------------ | ------------------------- | -------------------------- |
| **基础设施** | CPU、内存、磁盘、网络     | Prometheus + Node Exporter |
| **应用层**   | QPS、延迟、错误率、饱和度 | Prometheus + Micrometer    |
| **业务层**   | 订单量、支付成功率        | 自定义埋点 + Grafana       |
| **日志**     | 错误日志、慢查询          | ELK (Elasticsearch)        |
| **链路**     | 请求经过哪些服务，哪步慢  | Jaeger / SkyWalking        |

### 实现示例

```python
from prometheus_client import Counter, Histogram, start_http_server
import time

# 定义指标
REQUEST_COUNT = Counter('http_requests_total', 'Total requests', ['method', 'endpoint'])
REQUEST_LATENCY = Histogram('http_request_duration_seconds', 'Request latency')

# 埋点
@app.get("/order/{id}")
async def get_order(id: int):
    start = time.time()
    REQUEST_COUNT.labels(method="GET", endpoint="/order").inc()  # 计数+1
    
    try:
        result = await fetch_order(id)
        return result
    except Exception as e:
        REQUEST_COUNT.labels(method="GET", endpoint="/order_error").inc()
        raise
    finally:
        REQUEST_LATENCY.observe(time.time() - start)  # 记录耗时

# Prometheus 定期抓取这些指标，Grafana 展示图表
```

**监控大盘示例**：
```
┌─────────────────────────────────────────┐
│  订单服务 QPS: 1200/s    健康           │
│  平均延迟: 45ms          🟢 正常        │
│  错误率: 0.1%            🟢 正常        │
│  CPU: 65%                🟡 警告        │
│  ─────────────────────────────────────  │
│  告警：实例 order-003 内存使用 > 90%    │
└─────────────────────────────────────────┘
```

## 3. 负载均衡（Load Balancing）

### 类比：智能派单系统
```
用户下单（朝阳区）：
├─ 候选骑手A：距离2km，当前负载80% → 得分 75
├─ 候选骑手B：距离1km，当前负载50% → 得分 90  ← 派给他！
└─ 候选骑手C：距离3km，当前负载30% → 得分 60
```

### 技术定义
> **将请求合理分配到多个服务实例，避免单点过载**

### 负载均衡层级

```
┌─────────────────────────────────────────┐
│  第1层：DNS 负载均衡（地理级别）          │
│  北京用户 → 北京机房，上海用户 → 上海机房  │
├─────────────────────────────────────────┤
│  第2层：LVS/Nginx（网络层/反向代理）      │
│  将流量分发到不同机器                     │
├─────────────────────────────────────────┤
│  第3层：客户端负载均衡（应用层）           │
│  服务A调用服务B时，自己选实例              │
└─────────────────────────────────────────┘
```

### 常用算法

| 算法                             | 说明                     | 适用场景     |
| -------------------------------- | ------------------------ | ------------ |
| **轮询** (Round Robin)           | A → B → C → A...         | 实例性能相同 |
| **加权轮询**                     | 性能好的多分配           | 异构机器     |
| **最少连接** (Least Connections) | 选当前请求最少的         | 长连接服务   |
| **IP哈希**                       | 同一IP总是路由到同一实例 | 需要会话保持 |
| **一致性哈希**                   | 节点变化时影响最小       | 缓存服务     |

### 实现示例

#### Nginx 配置（反向代理层）
```nginx
upstream order_service {
    least_conn;  # 最少连接算法
    
    server 10.0.1.5:8080 weight=5;  # 性能好，权重高
    server 10.0.1.6:8080 weight=3;
    server 10.0.1.7:8080 backup;     # 备用，其他挂了才用
    
    keepalive 32;  # 长连接复用
}

server {
    location /api/orders {
        proxy_pass http://order_service;
    }
}
```

#### 客户端负载均衡（微服务内部）
```python
import random
from fastapi import FastAPI
import httpx

app = FastAPI()

# 从服务发现获取实例（模拟）
ORDER_SERVICES = [
    "http://10.0.1.5:8080",
    "http://10.0.1.6:8080",
    "http://10.0.1.7:8080"
]

class LoadBalancer:
    def __init__(self):
        self.index = 0
        self.weights = [5, 3, 2]  # 加权轮询
    
    def round_robin(self):
        """简单轮询"""
        instance = ORDER_SERVICES[self.index]
        self.index = (self.index + 1) % len(ORDER_SERVICES)
        return instance
    
    def random_select(self):
        """随机"""
        return random.choice(ORDER_SERVICES)
    
    def least_response_time(self):
        """选响应最快的（需要维护统计信息）"""
        # 实际实现会记录每个实例的延迟
        return min(ORDER_SERVICES, key=lambda x: self.get_latency(x))

lb = LoadBalancer()

@app.get("/proxy/order/{id}")
async def proxy_order(id: int):
    # 负载均衡选择实例
    target = lb.round_robin()
    
    # 调用具体实例
    async with httpx.AsyncClient() as client:
        response = await client.get(f"{target}/order/{id}")
        return response.json()
```

## 三者协作关系

```
┌─────────────────────────────────────────┐
│           客户端请求到来                 │
└─────────────────────────────────────────┘
                   ↓
┌─────────────────────────────────────────┐
│  1. 服务发现：查询注册中心                │
│     "有哪些可用的订单服务？"              │
│     → 返回：[10.0.1.5, 10.0.1.6, 10.0.1.7] │
└─────────────────────────────────────────┘
                   ↓
┌─────────────────────────────────────────┐
│  2. 负载监控：获取实例状态                │
│     "10.0.1.5 CPU 90%，10.0.1.6 健康"   │
│     → 过滤掉不健康的                     │
└─────────────────────────────────────────┘
                   ↓
┌─────────────────────────────────────────┐
│  3. 负载均衡：选择最优实例                │
│     "10.0.1.6 负载最低，派给它"          │
│     → 转发请求                          │
└─────────────────────────────────────────┘
                   ↓
           返回响应给客户端
```

## 云原生时代的简化（Kubernetes）

在现代 K8s 环境中，这三者被大大简化：

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: order-service
spec:
  replicas: 3  # 3个实例，自动负载均衡
  template:
    spec:
      containers:
        - name: order
          image: order:v1
          resources:  # 负载监控基础
            limits:
              cpu: "500m"
              memory: "512Mi"
          livenessProbe:  # 健康检查（服务发现用）
            httpGet:
              path: /health
              port: 8080
---
apiVersion: v1
kind: Service
metadata:
  name: order-service
spec:
  selector:
    app: order
  ports:
    - port: 80
  # ↑ 自动服务发现 + 内置轮询负载均衡
```

**K8s 自动搞定**：
- ✅ 服务发现：DNS 名 `order-service` 自动解析到3个Pod IP
- ✅ 负载监控：自动收集指标，不健康自动重启
- ✅ 负载均衡：kube-proxy 自动轮询分发

## 一句话总结

| 概念         | 一句话                     | 关键工具                  |
| ------------ | -------------------------- | ------------------------- |
| **服务发现** | "服务在哪？是否活着？"     | Consul, etcd, K8s DNS     |
| **负载监控** | "服务累不累？要不要报警？" | Prometheus, Grafana       |
| **负载均衡** | "请求派给谁最合理？"       | Nginx, Envoy, K8s Service |
