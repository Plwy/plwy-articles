

# Raw、YUV、RGB、JPG、PNG 关系

## **图像数据格式基础**

### 1. RAW格式

- **定义**：传感器（Sensor）直接输出的原始数字信号，未经过插值或压缩处理，也称为 **Bayer格式**。
- **Bayer排列**：每个像素仅记录 **R、G、B 中的一种颜色**，且相邻像素按特定规律排列（常见为 **GRBG** 格式：每2×2的4个像素中，包含2个G、1个R、1个B）。
- **数据量计算**： 以 **200万像素（2M）、RAW10格式（每像素10bit）** 为例： 单帧数据量 = 2M × 10bit = 20Mbit； 30帧/秒的码率 = 20Mbit × 30 ≈ **600Mbps**（未压缩的高带宽需求）。
- **特点**：数据原始、信息量大，但需后续处理（如插值计算RGB）才能生成可视图像。

### 2. RGB格式

- **定义**：通过插值算法从RAW数据计算得到的格式，**每个像素包含完整的R、G、B三通道颜色信息**。
- **常见子格式**： **RGB888**：每个通道8bit，单像素占用 8(R)+8(G)+8(B) = **24bit（3字节）**； 2M像素的单帧数据量 = 2M × 24bit = 48Mbit，30帧码率 ≈ **1.44Gbps**（更高带宽）。 **RGB565**：R（5bit）+G（6bit）+B（5bit），单像素占用 **16bit（2字节）**（牺牲部分色彩精度以降低数据量）。
- **用途**：直接用于屏幕显示或图像处理，但数据量较大。

### 3. YUV格式

- **定义**：与RGB不同的颜色编码方式，通过 **亮度（Y）和色度（U/V）分离** 表示颜色，更符合人眼对亮度的敏感特性。
- **核心优势**：色度（U/V）可降采样（如YUV420仅保留1/4色度数据），大幅减少数据量。
- **常见子格式**： **YUV444**：Y、U、V各通道分辨率相同（无降采样，数据量接近RGB）； **YUV422**：色度水平降采样（每2个像素共享1组U/V）； **YUV420**：色度水平和垂直均降采样（每4个像素共享1组U/V，最常用，数据量最小）。
- **与RGB转换**：可通过数学算法（如BT.601/BT.709标准）互相转换，但会损失少量色彩信息。

### 4. JPG/PNG格式

- **JPG（JPEG）**： **原理**：基于有损压缩算法（去除高频冗余数据），通过调整压缩比平衡文件大小与图像质量。 **示例**：2M像素的RGB888图像（48Mbit）以10:1压缩后，大小≈4.8Mbit（码率144Mbps），适合存储和传输，但放大后可能出现模糊或块效应。 **依赖库**：存储RGB/YUV数据为JPG需使用开源库（如libjpeg或libjpeg-turbo）。
- **PNG**： **原理**：无损压缩（保留全部原始数据），支持透明通道（Alpha），适合需要高保真的场景（如图标、截图）。 **对比**：文件体积通常大于JPG，但无画质损失。

### 5. 核心差异总结

| 格式 | 数据内容              | 是否插值 | 数据量（示例2M像素）        | 适用场景                   |
| ---- | --------------------- | -------- | --------------------------- | -------------------------- |
| RAW  | 单通道（R/G/B之一）   | 否       | ~600Mbps（RAW10，30帧）     | 传感器原始输出，需后处理   |
| RGB  | 完整三通道（R+G+B）   | 是       | ~1.44Gbps（RGB888，30帧）   | 屏幕显示、直接图像处理     |
| YUV  | 亮度+降采样色度       | 是       | 低于RGB（如YUV420更小）     | 视频编码、传输（节省带宽） |
| JPG  | 有损压缩的RGB/YUV衍生 | 是       | 可调（如10:1压缩后4.8Mbit） | 照片存储、网络传输         |
| PNG  | 无损压缩的RGB/YUV衍生 | 是       | 较大（无损）                | 高保真图像（如截图、图标） |

# **YUV数据格式详解**

### 1. 基础概念

YUV通过分离 **亮度（Y）** 和 **色度（U/V）** 编码，利用人眼对亮度更敏感的特性，通过降低色度分辨率（如YUV420）减少数据量，同时保持主观观感接近RGB。

### 2. 常见子格式

- **YUV444**：Y、U、V均为原始分辨率（无降采样，数据量≈RGB）。
- **YUV422**：色度水平降采样（每2个像素共享1组U/V，数据量约为RGB的2/3）。
- **YUV420**：色度水平和垂直均降采样（每4个像素共享1组U/V，数据量约为RGB的1/2，最常用）。

### 3. 与RGB的转换

- **转换算法**：需遵循标准（如BT.601用于标清视频，BT.709用于高清视频），公式涉及矩阵运算（例如：Y = 0.299R + 0.587G + 0.114B，U/V类似）。
- **工具支持**：OpenCV等库提供直接的YUV与Mat（图像矩阵）转换接口。

# 音视频开发关键技术

## 1.FFmpeg

FFmpeg可以称得上音视频应用程序的瑞士军刀，从采集到播放贯穿了视频全链条。

现在比较火的直播、IPTV、视频会议、短视频等，都要依赖于音视频的一个音视频开发库--ffmppeg，它是音视频领域必须要了解而且要掌握的一个知识点。对视频进行转码、剪辑、加入动效等。

**定位**：开源的音视频处理“瑞士军刀”，覆盖 **采集、编码、解码、转码、剪辑、滤镜、播放** 等全流程。

**典型应用**：

- 视频转码（如RAW/YUV→H.264 MP4）；
- 直播推流/拉流；
- 添加字幕、水印、动效；
- 支持几乎所有主流格式（如H.264/H.265、MP4/FLV/TS）。

## **2.流媒体客户端**

### **rtmp**

> RTMP（Real Time Message Protocol） 有 Adobe 公司提出，用来解决多媒体数据传输流的多路复用（Multiplexing）和分包（packetizing）的问题，优势在于低延迟，稳定性高，支持所有摄像头格式，浏览器加载 flash插件就可以直接播放。

### **rtsp**

> RTSP （Real-Time Stream Protocol）由Real Networks 和 Netscape共同提出的，基于文本的多媒体播放控制协议。RTSP定义流格式，流数据经由RTP传输；RTSP实时效果非常好，适合视频聊天，视频监控等方向。

### **hls**

> HLS （ HTTP Live Streaming）苹果公司提出的流媒体协议，直接把流媒体切片成一段段，信息保存到m3u列表文件中，可以将不同速率的版本切成相应的片；播放器可以直接使用http协议请求流数据，可以在不同速率的版本间自由切换，实现无缝播放；省去使用其他协议的烦恼。缺点是延迟大小受切片大小影响，不适合直播，适合视频点播。
> 总结：HLS 延迟大，适合视频点播；RTSP虽然实时性最好，但是实现复杂，适合视频聊天和视频监控；RTMP强在浏览器支持好，加载flash插件后就能直接播放，所以非常火，相反在浏览器里播放rtsp就很困难了。

## 4.WebRTC

**WebRTC（Web Real-Time Communications）** 是由谷歌开源并推进纳入W3C标准的一项音视频技术，旨在通过点对点的方式，实现了在web端的低时延音视频通话的能力，因此需要web端低时延音视频的场景都可以利用webrtc技术来实现，譬如在线教育和远程医疗。

与Web世界经典的B/S架构最大的不同是，WebRTC的通信不经过服务器，而直接与客户端连接，在节省服务器资源的同时，提高通信效率。为了做到这点，一个典型的WebRTC通信过程，包含四个步骤：**找到对方，进行协商，建立连接，开始通讯**。
